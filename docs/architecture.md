# Architecture

AIKernel.Doom is organized as a demo-grade AIKernel application rather than as a
game engine package. The goal is to show how a WASM process, WebGPU rendering,
runtime consent, telemetry, and an AI control loop can be wired together while
following the AIKernel Development Guidelines.

The design deliberately emphasizes:

- **Interface-Led Architecture (ILA)**: behavior is exposed through contracts
  before implementation details,
- **Provider-Observer-Operator (POO)**: side effects, observation, and execution
  are separated,
- **DAG Principle**: phase transitions and command arbitration are structured
  as deterministic, inspectable control flow,
- **Exceptionless Fail-Closed Principle**: missing assets, unavailable GPU
  surfaces, invalid WADs, or rejected consent do not silently continue,
- **Governance and Evidence**: runtime decisions are observable through status,
  overlay, copied logs, and optimizer telemetry.

## Responsibility Model

AIKernel.Doom follows the AIKernel development guideline emphasis on
Interface-Led Architecture and the Provider-Observer-Operator model.

### Provider

Provider code owns side effects and external boundaries, matching the guideline
rule that probabilistic or side-effecting behavior must be confined behind
Provider contracts.

- `DoomProvider` manages consent, lifecycle state, runtime preparation, and the
  capability-facing status surface.
- `DoomWasm` resolves ROM metadata and `doom.wasm` assets.
- `DoomWasm.Native` provides the C/WASM boundary for the DOOM engine.
- `DoomWeb` owns the browser runtime bridge, WebGPU surface, hosted asset
  manifest loading, and public prompt scripts.
- `WebGpuComputeProvider` represents the GPU execution and texture surface.

Provider code must fail closed. Missing WAD/model/WASM files, invalid WAD
headers, unavailable WebGPU, and unsupported browser features are reported as
runtime status and fallback state instead of being hidden.

### Observer

Observer code records and explains runtime behavior. It is intentionally
separate from action selection so telemetry cannot accidentally become a hidden
control dependency.

- `doom.status` emits a compact state string for human inspection.
- `doom.phase.check` emits a phase-focused snapshot.
- `copy.logs` and `Phase + Logs` gather console, runtime JSON, and static map
  hints.
- The debug overlay draws active detection regions and priorities.
- `DoomOptimizer` writes observer ROM telemetry under `artifacts/autoplay/`.

Observer code does not decide gameplay. It gives the developer enough evidence
to tune the Operator.

### Operator

Operator code turns observed state into actions. It should be deterministic,
bounded, and replayable from recorded state wherever possible.

- `IAutoplayStrategy` maps `SensorFusion` to `ActionCommand`.
- Browser autoplay logic routes phases such as `OpeningHome`, `FirstDoor`, and
  `ComputerRoom`.
- The cooperative scheduler throttles tick/render/predict loops so the UI
  thread remains responsive.
- The action arbiter prevents lower-priority movement logic from overwriting
  high-priority door, combat, or emergency actions.

## Runtime Flow As A DAG

```text
User approval
  -> hosted asset validation
  -> doom.wasm instantiate
  -> DOOM1.WAD memory mount
  -> doom_init
  -> requestAnimationFrame loop
  -> doom_tick
  -> doom_render
  -> WebGPU texture or Canvas fallback
  -> perception sampling
  -> phase router
  -> autoplay action
  -> doom_input / doom_input_action
```

The runtime is not implemented as an opaque loop. Each arrow is a stable
boundary that can be observed, failed closed, or replaced by a test double.
This is the demo equivalent of an AIKernel Skeleton executed by Operators with
Providers attached at the edges.

## Package Boundaries

The demo uses AIKernel package concepts without making DOOM itself a package.

- `DoomCapabilities` exposes a capability-style surface.
- `DoomProvider` acts as the provider boundary.
- `DoomWeb` is deployable source for public demo hosts.
- `DoomOptimizer` is a development tool, not a runtime dependency.

## Fail-Closed Invariants

- No protected asset is loaded before explicit consent.
- No third-party binary runtime artifact is committed to source control.
- `doom.wasm` must be generated by Emscripten; fake binaries are not accepted.
- WebGPU is optional; Canvas/CPU fallback remains deterministic.
- AutoPlay actions are bounded to DOOM inputs only.
- Manual controls can override AutoPlay for debugging.
- Sense Only mode suppresses AI input while preserving sensing and telemetry.

These invariants are intentionally documented because they are the review
surface for guideline compliance. If a future change bypasses consent, hides a
missing asset, or lets low-priority movement overwrite a critical Use action,
it violates the architecture rather than merely changing gameplay behavior.

## Why JavaScript Owns The Web Control Loop

The browser is the only place where these surfaces meet at frame cadence:

- WebGPU texture ownership,
- OffscreenCanvas/worker availability,
- keyboard and virtual controller input,
- DOOM framebuffer memory,
- debug overlay rendering,
- copied diagnostics,
- consent-gated hosted assets.

For this demo, the JavaScript layer intentionally contains a rich reference
implementation. It is the most portable example of AIKernel-style runtime
observation and control in a constrained UI environment.
